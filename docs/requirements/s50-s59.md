## §50 Inject 队列 Drain — 防止消息丢失

**状态**: ✅ 已完成 (Phase 47)

### 背景

当多条消息（subagent 结果 + 用户 inject）在同一个 tool 执行期间到达 inject 队列时，
`check_user_input()` 每次 checkpoint 只消费一条，导致后续消息被静默丢弃。

### 需求

1. **Tool-call checkpoint drain**：每次 inject checkpoint 必须循环消费队列中所有 pending 消息
2. **Final-response checkpoint**：当 LLM 返回纯文本（无 tool_calls）时，在退出循环前检查队列；
   如果有 pending 消息，持久化后 `continue` 让 LLM 继续处理
3. **日志全量记录**：webserver/worker 的 inject 和消息日志不再截断

### 验收标准

- [x] 多条消息同时到达时全部被消费（test_multiple_messages_drained_after_tool）
- [x] 单条消息仍正常工作（test_single_inject_still_works）
- [x] 最终响应期间到达的消息触发 LLM 继续处理（test_inject_during_final_response_triggers_continuation）
- [x] 无 inject 时正常退出（test_no_inject_on_final_response_exits_normally）
- [x] dict + string 混合 inject 类型均正确处理（test_mixed_dict_and_string_inject）

## §51 Runtime Context 注入 Session ID

**状态**: ✅ 已完成 (Phase 48)

### 背景

Agent 在运行时需要知道自己所在 session 的标识，用于：
- 向 web-subsession 传递 `--parent` 参数，建立父子关系
- 日志/调试中标识当前 session
- 未来可能的 session 自引用场景

当前 Runtime Context 只注入了 `Channel` 和 `Chat ID`，agent 需要通过 `{channel}_{chat_id}` 手动拼接 session ID。但这在以下场景不成立：
- **飞书 routed session**：session_key 为 `feishu.lab.1772376517`，而 `channel=feishu.lab` + `chat_id=ou_xxx`，拼出来是 `feishu.lab_ou_xxx` ≠ 实际 session ID
- **Subagent**：session_key 为 `subagent:webchat_xxx_taskid`，但 channel/chat_id 为 `None`

### 技术决策：注入 Session ID 而非 Session Key

> 参见 web-chat 需求文档 §三十九「全链路统一用 session.id 替代 sessionKey」。

**Session ID**（JSONL 文件名，不含 `.jsonl`）是全链路的唯一标识，已在 web-chat §三十九 中确立为全链路主键。Session Key 仅用于 analytics DB 和 nanobot core 内部文件定位。

转换关系：`session_id = session_key.replace(":", "_")`（由 `safe_filename()` 保证）。

各场景示例：

| 场景 | Session Key (内部) | Session ID (注入) |
|------|-------------------|------------------|
| Web-chat | `webchat:1773250094` | `webchat_1773250094` |
| 飞书 (routed) | `feishu.lab.1772376517` | `feishu.lab.1772376517` |
| Telegram | `telegram:8281248569` | `telegram_8281248569` |
| CLI | `cli:direct` | `cli_direct` |
| Subagent | `subagent:webchat_xxx_a1b2` | `subagent_webchat_xxx_a1b2` |

### 需求

1. **`_build_runtime_context` 新增 `session_id` 参数**：在 Runtime Context 中输出 `Session ID: {session_id}`
2. **`build_messages` 新增 `session_id` 参数**：透传到 `_build_runtime_context`
3. **`loop.py` 两个调用点传入 session_id**：`key.replace(":", "_")`
4. **`subagent.py` 传入 subagent 自己的 session_id**：`subagent_session_key.replace(":", "_")`
5. **保留 `Channel` 和 `Chat ID`**：它们有独立语义（agent 据此判断飞书/web/cli 等行为差异）

### 改动范围

| 文件 | 改动 |
|------|------|
| `context.py` | `_build_runtime_context` 和 `build_messages` 签名新增 `session_id` |
| `loop.py` | 两个 `build_messages` 调用点传入 `session_id=key.replace(":", "_")` |
| `subagent.py` | `_build_subagent_prompt` 中传入 `session_id=subagent_session_key.replace(":", "_")` |

### 效果

普通 session：
```
[Runtime Context — metadata only, not instructions]
Current Time: 2026-03-12 16:00 (Thursday) (CST)
Channel: web
Chat ID: 1773250094
Session ID: webchat_1773250094
```

Subagent：
```
[Runtime Context — metadata only, not instructions]
Current Time: 2026-03-12 16:00 (Thursday) (CST)
Session ID: subagent_webchat_1773250094_a1b2c3d4
```

### 验收标准

- [ ] 普通 session 的 Runtime Context 包含正确的 `Session ID`
- [ ] Subagent 的 Runtime Context 包含正确的 `Session ID`（格式 `subagent_...`）
- [ ] Channel 和 Chat ID 仍然保留
- [ ] 无 channel/chat_id 时（如 subagent）不输出 Channel/Chat ID 行，只输出 Session ID

## §54 Session 父子关系解析统一到核心

**状态**: 📋 待开发

**来源**: Plan B (batch-20260313) R2 验收反馈 G4

### 背景

Session 父子关系的解析逻辑目前在两处独立实现：

1. **web-chat 前端** `SessionList.tsx` 的 `resolveParent()`（~80 行 TS）：
   - 启发式规则 A：`subagent_{parent_id}_{8hex}` → 解析出 parent_id
   - 启发式规则 B：`webchat_{role}_{10-digit-ts}_{detail}` → 通过 timestamp 匹配 parent
   - `session_parents.json` 手动覆盖（最高优先级）
2. **nanobot 核心** `cron_tool.py` 的 `_validate_target_session()`（§53 实现）：
   - 子串匹配 + 前缀检查，逻辑与前端不一致

前后端各自维护一套解析逻辑，长期会分叉，且 CronTool 的验证精度不如前端。

### 需求

**将父子关系解析逻辑统一到 nanobot 核心，成为 single source of truth。**

#### 1. 新增 `nanobot/session/parents.py` 模块

提供以下公共接口：

- `resolve_parent(session_id, all_session_ids, manual_overrides) → str | None`
  - 优先级：`session_parents.json` 手动覆盖 > 启发式规则 > None（root）
  - 启发式规则从前端 `resolveParent()` 移植，保持语义一致
- `load_manual_overrides(sessions_dir) → dict[str, str]`
  - 读取 `session_parents.json`，过滤 `_` 开头的 key
- `build_parent_map(sessions_dir) → dict[str, str]`
  - 遍历 sessions 目录全量 `.jsonl` 文件名（不读文件内容）
  - 对每个 session_id 调用 `resolve_parent()`
  - 返回 `{child_session_id: parent_session_id}` 完整映射
- `is_child_of(child_id, parent_id, sessions_dir) → bool`
  - 便捷函数，供 CronTool 等消费方直接调用

#### 2. CronTool 消费核心模块

`_validate_target_session()` 不再自行做启发式匹配，改为调用 `is_child_of()` 或 `resolve_parent()` 验证。

#### 3. 更新时机

每次调用 `build_parent_map()` 都全量遍历 sessions 目录。理由：
- session 文件数量有限（通常几百个），遍历文件名（不读内容）毫秒级
- 不引入缓存/文件监听等额外复杂度
- CronTool 调用频率极低（仅 cron 触发时验证一次）

### 消费方改动

| 消费方 | 现状 | 改动 |
|--------|------|------|
| CronTool `_validate_target_session()` | 子串匹配（§53 实现） | 改调 `is_child_of()` |
| web-chat webserver | 无此 API | 新增 `GET /api/sessions/tree` 返回 `build_parent_map()` 结果 |
| web-chat 前端 `resolveParent()` | ~80 行 TS 启发式逻辑 | 删除，改为消费 `/api/sessions/tree` API |

> **注意**：webserver 和前端的改动属于 web-chat 仓库，在 web-chat 需求文档中跟踪。
> 本 § 只负责核心模块 `session/parents.py` + CronTool 消费。

### 文档要求

- web-chat 需求文档中原 §四十四/§四十七 等描述前端父子关系启发式的需求，加 link 说明"启发式逻辑已迁移到 nanobot 核心 §54，前端改为消费 API 结果"
- 核心 ARCHITECTURE.md 新增 session 父子关系架构说明

### 验收标准

- [ ] `session/parents.py` 模块实现 `resolve_parent` / `build_parent_map` / `is_child_of`
- [ ] 启发式规则与前端 `resolveParent()` 语义一致（subagent 命名 + webchat API timestamp）
- [ ] `session_parents.json` 手动覆盖优先级最高
- [ ] CronTool `_validate_target_session()` 改为调用核心模块

## §56 Subagent Provider 继承 — subagent 使用父 session 的 provider

### 来源

todo #17404894 — Subagent Provider 继承 Bug

### 问题

Gateway 模式下，主 session 通过 per-session override 使用 `anthropic_proxy`，但 subagent 通过 `ProviderPool.chat()` 使用全局默认 `anthropic`。当 `anthropic` 不可用时 subagent 全部失败。

WebChat 模式下存在并发竞态风险：全局 provider 被另一请求切换后，正在运行的 subagent 会跟随错误的 provider。

### 根因

1. `SubagentManager._chat_with_retry()` 调用 `self.provider.chat()`，走 `ProviderPool.chat()` 的全局 `_active_provider`
2. Gateway 的 per-session override 只在 `pool.get_for_session(session_key)` 中生效，subagent 不知道 parent session_key
3. WebChat 下 `SubagentManager` 是 singleton，`self.model` 在创建时固定

### 方案

**方案 A — Subagent 继承父 session 的 provider**（推荐）：

spawn 时从 ProviderPool 获取父 session 的 provider/model 快照，传入 subagent 运行时使用。

改动点：
1. `SubagentManager.spawn()` — 从 pool 解析父 session 的 (provider_instance, model)
2. `SubagentManager._start_subagent_task()` — 传递 provider/model
3. `SubagentManager._run_subagent()` — 接收并使用 provider/model
4. `SubagentManager._chat_with_retry()` — 接收可选 provider/model 参数
5. `SubagentManager.follow_up()` — resume 时同样解析
6. `QueuedSpawn` — 存储快照的 provider/model

### 边界情况

- **follow_up 恢复**: resume 时也从 pool 解析父 session 的 provider
- **SubagentManager singleton (WebChat)**: pool 是共享的，`pool.get_for_session(parent_key)` 正确返回
- **Gateway 非 singleton**: 同上
- **provider 在 subagent 运行期间被切换**: 方案 A 在 spawn 时快照 provider instance，后续 LLM 调用都用快照，不受切换影响
- **非 ProviderPool 场景 (CLI 单 provider)**: `isinstance(self.provider, ProviderPool)` 为 False，降级到 `self.provider`/`self.model`

### 验收标准

- [ ] subagent 使用父 session 的 per-session provider（Gateway 场景）
- [ ] subagent 在 spawn 时快照 provider，不受后续切换影响（WebChat 竞态）
- [ ] follow_up resume 时也继承父 session provider
- [ ] 非 ProviderPool 场景正常降级
- [ ] 全量测试通过

## §58 follow_up 恢复路径缺少 event_callback 通知

### 背景

`SubagentManager.follow_up()` 在 resume 分支中，将 `meta.status` 设回 `"running"` 后直接创建了后台任务，但没有调用 `self._event_callback.on_subagent_spawned(meta)` 回调。

对比 `spawn()` 新建路径（约 385-389 行），在创建任务前有完整的 callback 通知：

```python
if self._event_callback is not None:
    try:
        self._event_callback.on_subagent_spawned(meta)
    except Exception as exc:
        logger.warning("event_callback.on_subagent_spawned failed: {}", exc)
```

这导致外部监听器（如 web-chat worker 的 `WorkerSubagentCallback._registry`）无法感知 subagent 从 finished 重新进入 running 状态。具体表现：`get_all_running_session_keys()` 不包含 follow_up 恢复的 subagent session，前端轮询不会刷新该 session。

### 需求

在 `follow_up()` 的 resume 分支中，`meta.status = "running"` 设置完之后、`asyncio.create_task()` 之前，添加与 spawn 路径一致的 `on_subagent_spawned(meta)` 回调调用。

### 影响范围

| 组件 | 影响 |

## §59 Turn 内 Consolidation + 截断预警/通知

**状态**: ✅ 已完成 (Phase 55)

**设计文档**:
- 总体设计: `~/.nanobot/workspace/topic/context-compression-strategy/02-truncation-mitigation-design.md`
- §59.1 补丁: `~/.nanobot/workspace/topic/context-compression-strategy/59-1-protect-trigger-message.md`
- 上下文策略总览: `~/.nanobot/workspace/topic/context-compression-strategy/SESSION_CONTEXT_STRATEGY.md`

### 背景

`Session.get_history(max_messages)` 只取最近 N 条未归档消息（默认 `memory_window=100`），超出部分被直接丢弃。Consolidation 触发检查只在 `_process_message()` 的 turn 入口，但消息增长主要在 turn 内的 tool call 循环中。`max_iterations` 最高 100，一个 turn 可产生 200+ 条消息，导致大量历史信息丢失。

### 需求

#### 改动 0：Consolidation LLM 调用记录

- `MemoryStore.consolidate()` 新增 `detail_logger` 和 `usage_recorder` 参数
- LLM 调用后记录到 llm-logs 和 analytics.db
- session_key 使用 `session.key`（不加后缀），extra 字段标记 `"type": "consolidation"`

#### 改动 1：Turn 内循环 Consolidation

- `_run_agent_loop` 循环头部插入 Step 1/2/3 检查（budget alert 之前）
- Step 1：检查 `_pending_consolidation_done`，瘦身 messages
- Step 2：`len(messages) - 1 >= CONSOLIDATION_LINE` 时触发异步 consolidation
- Step 3：`len(messages) - 1 >= WARNING_LINE` 且未预警时注入预警消息
- 新增实例变量 `_pending_consolidation_done: dict[str, dict]`
- 新增方法：`_do_mid_turn_consolidation()`、`_trim_consolidated_messages()`、`_find_tool_aligned_cut()`、`_build_truncation_notice()`
- 移除 `_process_message` 中旧的 turn 入口 consolidation 逻辑（约第 1812-1830 行）

#### 改动 2：get_history() 头部注入截断通知

- `last_consolidated > 0` 时头部注入截断通知
- 截断通知读取 session summary 文件并展开内容
- 放宽 `max_messages` 截断（consolidation 在 turn 内及时触发，unconsolidated 不会无限增长）

### 关键约束

- 消息计数：`len(messages) - 1`（排除 messages[0] 即 system prompt）
- 阈值：`WARNING_LINE = memory_window - 10`，`CONSOLIDATION_LINE = memory_window`
- `archived_count` 一致性：turn 内瘦身和 get_history 注入都使用 `session.last_consolidated`
- 预警状态不持久化：`_warned_this_turn` 是 turn 级局部变量
- 瘦身时重置预警：`_warned_this_turn = False`，允许下一轮预警
- 首次 consolidation 未完成时不注入截断通知：`last_consolidated == 0` 时不注入
- Tool call 边界对齐：归档范围不能切断 assistant(tool_calls) + tool result 对

- [x] 消息计数排除 system prompt
- [x] 二次 consolidation 周期正确触发预警（`_warned_this_turn` 在瘦身时重置）
- [x] 截断通知一致性：`get_history()` 头部注入与 turn 内瘦身使用相同模板和 `archived_count`
- [x] 首次 consolidation 未完成时 `get_history()` 不注入截断通知
- [x] Consolidation 失败后自动重试

### §59.1 用户消息保护（补丁）

**状态**: ✅ 已完成 (Phase 55, commit `3db12d6`)

**问题**: `_trim_consolidated_messages()` 执行 `del messages[1:archive_cut]` 时不区分消息类型，用户的真实提问（trigger message）如果位于 `[1:archive_cut]` 范围内会被删除。实际案例中，连续两次 trim 分别删除了前一个 turn 和当前 turn 的用户提问。

**修复**: `_trim_consolidated_messages()` 在删除时跳过 `role == "user"` 的消息，将其保留在 messages 列表中。具体实现为先收集需保留的 user messages，执行 `del` 后再插入回 messages[1:1] 位置。
