## §50 Inject 队列 Drain — 防止消息丢失

**状态**: ✅ 已完成 (Phase 47)

### 背景

当多条消息（subagent 结果 + 用户 inject）在同一个 tool 执行期间到达 inject 队列时，
`check_user_input()` 每次 checkpoint 只消费一条，导致后续消息被静默丢弃。

### 需求

1. **Tool-call checkpoint drain**：每次 inject checkpoint 必须循环消费队列中所有 pending 消息
2. **Final-response checkpoint**：当 LLM 返回纯文本（无 tool_calls）时，在退出循环前检查队列；
   如果有 pending 消息，持久化后 `continue` 让 LLM 继续处理
3. **日志全量记录**：webserver/worker 的 inject 和消息日志不再截断

### 验收标准

- [x] 多条消息同时到达时全部被消费（test_multiple_messages_drained_after_tool）
- [x] 单条消息仍正常工作（test_single_inject_still_works）
- [x] 最终响应期间到达的消息触发 LLM 继续处理（test_inject_during_final_response_triggers_continuation）
- [x] 无 inject 时正常退出（test_no_inject_on_final_response_exits_normally）
- [x] dict + string 混合 inject 类型均正确处理（test_mixed_dict_and_string_inject）

## §51 Runtime Context 注入 Session ID

**状态**: ✅ 已完成 (Phase 48)

### 背景

Agent 在运行时需要知道自己所在 session 的标识，用于：
- 向 web-subsession 传递 `--parent` 参数，建立父子关系
- 日志/调试中标识当前 session
- 未来可能的 session 自引用场景

当前 Runtime Context 只注入了 `Channel` 和 `Chat ID`，agent 需要通过 `{channel}_{chat_id}` 手动拼接 session ID。但这在以下场景不成立：
- **飞书 routed session**：session_key 为 `feishu.lab.1772376517`，而 `channel=feishu.lab` + `chat_id=ou_xxx`，拼出来是 `feishu.lab_ou_xxx` ≠ 实际 session ID
- **Subagent**：session_key 为 `subagent:webchat_xxx_taskid`，但 channel/chat_id 为 `None`

### 技术决策：注入 Session ID 而非 Session Key

> 参见 web-chat 需求文档 §三十九「全链路统一用 session.id 替代 sessionKey」。

**Session ID**（JSONL 文件名，不含 `.jsonl`）是全链路的唯一标识，已在 web-chat §三十九 中确立为全链路主键。Session Key 仅用于 analytics DB 和 nanobot core 内部文件定位。

转换关系：`session_id = session_key.replace(":", "_")`（由 `safe_filename()` 保证）。

各场景示例：

| 场景 | Session Key (内部) | Session ID (注入) |
|------|-------------------|------------------|
| Web-chat | `webchat:1773250094` | `webchat_1773250094` |
| 飞书 (routed) | `feishu.lab.1772376517` | `feishu.lab.1772376517` |
| Telegram | `telegram:8281248569` | `telegram_8281248569` |
| CLI | `cli:direct` | `cli_direct` |
| Subagent | `subagent:webchat_xxx_a1b2` | `subagent_webchat_xxx_a1b2` |

### 需求

1. **`_build_runtime_context` 新增 `session_id` 参数**：在 Runtime Context 中输出 `Session ID: {session_id}`
2. **`build_messages` 新增 `session_id` 参数**：透传到 `_build_runtime_context`
3. **`loop.py` 两个调用点传入 session_id**：`key.replace(":", "_")`
4. **`subagent.py` 传入 subagent 自己的 session_id**：`subagent_session_key.replace(":", "_")`
5. **保留 `Channel` 和 `Chat ID`**：它们有独立语义（agent 据此判断飞书/web/cli 等行为差异）

### 改动范围

| 文件 | 改动 |
|------|------|
| `context.py` | `_build_runtime_context` 和 `build_messages` 签名新增 `session_id` |
| `loop.py` | 两个 `build_messages` 调用点传入 `session_id=key.replace(":", "_")` |
| `subagent.py` | `_build_subagent_prompt` 中传入 `session_id=subagent_session_key.replace(":", "_")` |

### 效果

普通 session：
```
[Runtime Context — metadata only, not instructions]
Current Time: 2026-03-12 16:00 (Thursday) (CST)
Channel: web
Chat ID: 1773250094
Session ID: webchat_1773250094
```

Subagent：
```
[Runtime Context — metadata only, not instructions]
Current Time: 2026-03-12 16:00 (Thursday) (CST)
Session ID: subagent_webchat_1773250094_a1b2c3d4
```

### 验收标准

- [ ] 普通 session 的 Runtime Context 包含正确的 `Session ID`
- [ ] Subagent 的 Runtime Context 包含正确的 `Session ID`（格式 `subagent_...`）
- [ ] Channel 和 Chat ID 仍然保留
- [ ] 无 channel/chat_id 时（如 subagent）不输出 Channel/Chat ID 行，只输出 Session ID

## §52 /session 子命令体系 + session_id 全链路统一

### 背景

§十九引入了 `/session` 状态查询命令，§二十引入了 `/new` 归档方向反转和 session 命名简化。在此基础上扩展完整的 `/session` 子命令体系，并修复全链路使用 session_key 而非 session_id 导致的多个 bug。

### Session 识别统一规则

> **所有涉及 session 识别的场景（列表、切换、归档、摘要、缓存引用、路由表值等），统一使用 Session ID（文件名 stem），不使用 Session Key。**
>
> Session Key 仅在 nanobot core 内部（`get_or_create()`、analytics DB）中使用。

### 参数语法约定

| 前缀 | 含义 | 示例 |
|------|------|------|
| `#N` | 序号引用（来自最近一次 list） | `#3` |
| `%session_id` | session_id 直接引用 | `%feishu.lab.1772855249` |
| 纯数字 | 语境相关数值参数（条数、范围等） | `5`、`5-10` |

### 子命令列表

| 子命令 | 用法 | 说明 |
|--------|------|------|
| (无) | `/session` | 显示当前 session 状态 |
| `list` | `/session list [N]` | 列出最近 N 个 session（默认 10） |
| `list` | `/session list M-N` | 列出第 M 到第 N 个 session |
| `list` | `/session list --all` | 列出所有 session（含已归档） |
| `switch` | `/session switch <#N\|%id>` | 切换到指定 session |
| `name` | `/session name <名称>` | 给当前 session 命名 |
| `summary` | `/session summary [#N\|%id] [条数]` | 显示 session 摘要 |
| `done` | `/session done [#N\|%id]` | 归档 session |
| `undone` | `/session undone [#N\|%id]` | 取消归档 |
| `help` | `/session help` | 显示帮助 |

### 影响范围

| 文件 | 改动 |
|------|------|
| `session/manager.py` | `list_sessions()` 增加 `session_id` 字段；`get_session_message_count()` 改为接受 session_id；`switch_session()` 改为接受 session_id |
| `agent/loop.py` | `_last_session_list` 缓存 session_id；`_resolve_session_arg()` 返回 session_id 支持 `%` 语法；所有子命令适配 session_id；新增 `help`/`--all`/范围/summary 条数 |
| `tests/test_session_commands.py` | 全面更新测试适配 session_id + 新增功能测试 |
| `docs/architecture/core-loop.md` | §二十八末尾增加 "Session 识别统一规则" 提醒 |

### 验收标准

## §53 Cron target_session 修复 — session_id 统一 + subagent 支持

**状态**: 🔧 进行中

Plan B 验收（batch-20260313）发现 cron `target_session` 功能存在 4 项问题：

1. **F1**: `_validate_target_session()` 不支持 subagent session — `startswith(self._session_key)` 匹配失败
2. **F2**: target_session 内部使用 session_key 格式（`:`分隔），与 §51 确立的全链路 session_id 规范冲突
3. **F3**: cron SKILL.md 缺少 target_session 参数文档
4. **F6**: 架构文档缺少 session_id 在 tool 层面的规范说明

### 需求

1. **CronTool `set_context()` 新增 `session_id` 参数**：存储为 `self._session_id`
2. **`_validate_target_session()` 重写**：基于 session_id 比较
   - 自身 session_id 完全匹配 → 允许
   - target 包含自身 session_id 作为子串（subagent 场景）→ 允许
   - target 以 `cron_` 开头 → 允许
   - 含 `:` → 拒绝（session_key 格式不接受）
   - 否则拒绝
3. **CronPayload.target_session 存储 session_id 格式**
4. **CronService._execute_job() 中 session_id→session_key 转换**：`id.replace("_", ":", 1)` 后传给 `send_to_session()`
5. **cron SKILL.md 补充 target_session 文档**
6. **架构文档补充**：tool 参数接口层统一使用 session_id 格式；不使用 system role 注入 cron 消息（litellm 兼容性约束）

### 约束

- **不使用 system role 注入 cron 消息**：litellm 有 system prompt 组装问题，cron 消息以 user role 注入

### 验收标准

- [ ] subagent session_id 通过 target_session 校验
- [ ] 自身 session_id 通过校验
- [ ] cron session_id 通过校验

## §54 Session 父子关系解析统一到核心

**状态**: 📋 待开发

**来源**: Plan B (batch-20260313) R2 验收反馈 G4

### 背景

Session 父子关系的解析逻辑目前在两处独立实现：

1. **web-chat 前端** `SessionList.tsx` 的 `resolveParent()`（~80 行 TS）：
   - 启发式规则 A：`subagent_{parent_id}_{8hex}` → 解析出 parent_id
   - 启发式规则 B：`webchat_{role}_{10-digit-ts}_{detail}` → 通过 timestamp 匹配 parent
   - `session_parents.json` 手动覆盖（最高优先级）
2. **nanobot 核心** `cron_tool.py` 的 `_validate_target_session()`（§52 实现）：
   - 子串匹配 + 前缀检查，逻辑与前端不一致

前后端各自维护一套解析逻辑，长期会分叉，且 CronTool 的验证精度不如前端。

### 需求

**将父子关系解析逻辑统一到 nanobot 核心，成为 single source of truth。**

#### 1. 新增 `nanobot/session/parents.py` 模块

提供以下公共接口：

- `resolve_parent(session_id, all_session_ids, manual_overrides) → str | None`
  - 优先级：`session_parents.json` 手动覆盖 > 启发式规则 > None（root）
  - 启发式规则从前端 `resolveParent()` 移植，保持语义一致
- `load_manual_overrides(sessions_dir) → dict[str, str]`
  - 读取 `session_parents.json`，过滤 `_` 开头的 key
- `build_parent_map(sessions_dir) → dict[str, str]`
  - 遍历 sessions 目录全量 `.jsonl` 文件名（不读文件内容）
  - 对每个 session_id 调用 `resolve_parent()`
  - 返回 `{child_session_id: parent_session_id}` 完整映射
- `is_child_of(child_id, parent_id, sessions_dir) → bool`
  - 便捷函数，供 CronTool 等消费方直接调用

#### 2. CronTool 消费核心模块

`_validate_target_session()` 不再自行做启发式匹配，改为调用 `is_child_of()` 或 `resolve_parent()` 验证。

#### 3. 更新时机

每次调用 `build_parent_map()` 都全量遍历 sessions 目录。理由：
- session 文件数量有限（通常几百个），遍历文件名（不读内容）毫秒级
- 不引入缓存/文件监听等额外复杂度
- CronTool 调用频率极低（仅 cron 触发时验证一次）

### 消费方改动

| 消费方 | 现状 | 改动 |
|--------|------|------|
| CronTool `_validate_target_session()` | 子串匹配（§52 实现） | 改调 `is_child_of()` |
| web-chat webserver | 无此 API | 新增 `GET /api/sessions/tree` 返回 `build_parent_map()` 结果 |
| web-chat 前端 `resolveParent()` | ~80 行 TS 启发式逻辑 | 删除，改为消费 `/api/sessions/tree` API |

> **注意**：webserver 和前端的改动属于 web-chat 仓库，在 web-chat 需求文档中跟踪。
> 本 § 只负责核心模块 `session/parents.py` + CronTool 消费。

### 文档要求

- web-chat 需求文档中原 §四十四/§四十七 等描述前端父子关系启发式的需求，加 link 说明"启发式逻辑已迁移到 nanobot 核心 §53，前端改为消费 API 结果"
- 核心 ARCHITECTURE.md 新增 session 父子关系架构说明

### 验收标准

- [ ] `session/parents.py` 模块实现 `resolve_parent` / `build_parent_map` / `is_child_of`
- [ ] 启发式规则与前端 `resolveParent()` 语义一致（subagent 命名 + webchat API timestamp）
- [ ] `session_parents.json` 手动覆盖优先级最高
- [ ] CronTool `_validate_target_session()` 改为调用核心模块
- [ ] 单元测试覆盖：subagent 解析、webchat API session 解析、手动覆盖、root session、is_child_of
- [ ] 全量回归通过

## §55 Cron name 参数 + 消息格式优化

**状态**: 📋 待开发

**来源**: Plan B (batch-20260313) R2 验收反馈 G1 + G3 + G5

### 背景

1. **G1 消息内容重复**：`cron_tool.py _add_job()` 中 `name = message[:30]`，当 message ≤ 30 字符时 name == message，导致 executor 端消息中 job.name 和 message 重复显示
2. **G3 文档缺失**：`tz` 参数仅对 `cron_expr` 生效，不对 `at` 生效，但 SKILL.md 和 tool schema 未说明
3. **G5 session 列表无区分度**：所有 cron session 显示为 `[Scheduled Task] Timer finished.`

### 需求

#### 1. CronTool 暴露 `name` 参数

- tool schema 新增 `name` 参数（可选），description: "Short display name for the job (e.g. '午休提醒')"
- LLM 传入 name 时直接使用；未传时 fallback `message[:50]`
- `CronPayload` 或 job 创建逻辑相应适配

#### 2. Executor 消息格式简化

- 独立 cron session 消息格式改为：`⏰ {job.name}\n\n{job.payload.message}`
- 去掉 `[Scheduled Task] Timer finished.` 和 `Scheduled instruction:` 冗余文字
- send_to_session 前缀改为：`⏰ [cron:{source}] {message}`

#### 3. SKILL.md + tool schema 补充 tz 限制

- SKILL.md 追加说明：`tz` 仅对 `cron_expr` 生效，`at` 使用本地时间
- tool schema 中 `tz` 的 description 加限定

### 约束

- executor 消息格式改动涉及 web-chat 的 `commands.py`（GatewayCronExecutor），需在 web-chat 仓库同步修改
- 前端 `CronNotificationCard` 的检测逻辑（`[Scheduled Task` 前缀）需同步适配新格式

### 验收标准

- [ ] CronTool schema 包含 `name` 参数
- [ ] LLM 传入 name 时 job.name 使用传入值
- [ ] LLM 未传 name 时 job.name 为 message[:50]
- [ ] cron session 消息格式不再重复
- [ ] session 列表显示 job.name 而非千篇一律的 `[Scheduled Task] Timer finished.`
- [ ] SKILL.md 说明 tz + at 不兼容
- [ ] 全量测试通过
