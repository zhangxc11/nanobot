## §60 Streaming Timeout 修复与鲁棒性增强

**状态**: ✅ 已完成 (Phase 56)
**分支**: `fix/s60-timeout-and-robustness`

### 背景

API 代理（apia/ppapi）均不支持 streaming 透传，全量缓冲模式下 Claude Opus 大请求 TTFB 可达 192s，超过原 `read=120s` timeout。此外还存在多个鲁棒性问题：

1. **Timeout 不足**: `read=120s` 对全量缓冲模式不够，大请求直接超时
2. **截断死循环**: `finish_reason=length` 截断时 tool_call JSON 被 `json_repair` 静默修复为不完整参数，导致 agent 死循环
3. **Spawn 无法自定义 max_tokens**: subagent 固定使用默认 max_tokens，无法按需调整
4. **日志诊断信息不足**: retry/error 日志缺少 provider name/api_base/session_key，排查困难

### 需求

#### 改动 1: read timeout 120→300s

- `LiteLLMProvider._call_llm()` 中 `read` timeout 从 120s 调整为 300s
- 关闭 streaming（`stream=False`），因为代理都不支持 streaming 透传

#### 改动 2: usage missing warning

- `LiteLLMProvider._call_llm()` 在 response 缺少 usage 字段时记录 warning 日志
- 包含 `model`、`finish_reason`、`response_id` 等诊断信息

#### 改动 3: non-dict tool args 防御

- `AgentLoop._run_agent_loop()` 在处理 tool_calls 时，检查 `arguments` 是否为 dict
- 非 dict 时 skip 该 tool call 并注入错误提示

#### 改动 4: 截断检测（finish_reason=length + tool_calls → skip + inject split hint）

- `AgentLoop._run_agent_loop()` 在处理 LLM 响应时检测 `finish_reason == "length"`
- 当截断发生且存在 tool_calls 时，skip 所有 tool calls 并注入 split hint 提示 LLM 拆分请求
- 避免 `json_repair` 静默修复不完整 JSON 导致的死循环

#### 改动 5: spawn max_tokens 参数支持

- `SpawnTool` 新增 `max_tokens` 可选参数
- `SubagentManager.spawn()` 和 `_run_subagent()` 透传 `max_tokens`
- subagent 的 LLM 调用使用自定义 `max_tokens`（不传则使用 provider 默认值）

#### 改动 6: retry 日志增加 provider name/api_base/session_key

- `AgentLoop._run_agent_loop()` 中 retry 和 error 日志增加 provider 诊断信息
- 包含 `provider_name`、`api_base`、`session_key` 字段

#### 改动 7: registry non-dict params 防御 + audit 异常隔离

- `ToolRegistry.call_tool()` 对 `params` 进行 non-dict 防御
- audit 日志异常不影响工具执行（异常隔离）

#### 改动 8: detail_logger 增加 finish_reason/content/tool_calls 字段

- `DetailLogger` 记录 LLM 调用时增加 `finish_reason`、`content` 长度、`tool_calls` 数量等字段
- 便于事后分析截断和异常情况

### 决策记录

| 决策 | 理由 |
|------|------|
| 关闭 streaming（`stream=False` + `read=300s`） | 代理都不支持 streaming 透传，streaming 模式下超时更难控制 |
| 不保留 §60-diag 诊断代码 | 诊断阶段的临时代码不适合长期保留 |
| 不保留 partial usage extraction | usage 缺失时记录 warning 即可，不需要从 response 中强行提取 |
| 截断时 skip 而非 retry | retry 可能再次截断，skip + hint 让 LLM 主动拆分更有效 |

### 影响范围

| 组件 | 影响 |
|------|------|
| `nanobot/providers/litellm_provider.py` | read timeout 300s + usage missing warning |
| `nanobot/agent/loop.py` | 截断检测 + non-dict args 防御 + retry 日志增强 |
| `nanobot/agent/subagent.py` | max_tokens 参数透传 |
| `nanobot/agent/tools/spawn.py` | max_tokens 参数定义 |
| `nanobot/agent/tools/registry.py` | non-dict params 防御 + audit 异常隔离 |
| `nanobot/usage/detail_logger.py` | 增加 finish_reason/content/tool_calls 字段 |

### 验收标准

- [x] read timeout 300s 生效
- [x] usage 缺失时有 warning 日志
- [x] non-dict tool args 被防御，不导致崩溃
- [x] finish_reason=length + tool_calls 时 skip 并注入 split hint
- [x] spawn 支持 max_tokens 参数
- [x] retry/error 日志包含 provider 诊断信息
- [x] registry audit 异常不影响工具执行
- [x] detail_logger 记录 finish_reason 等新字段

|--------|------|------|

## §61 Timeout 智能诊断与恢复

**状态**: ✅ 已完成 (Phase 57)
**分支**: `feat/s61-timeout-diagnosis`

### 背景

§60 将 read timeout 从 120s 调整为 300s 解决了 Claude Opus 大请求 TTFB 问题，但 300s 是临时方案，存在两个不足：

1. **输出超 300s → 重试死循环**: max_retries=7，Timeout 也走 fast retry（1/2/4/8/16/30/30s），最坏 41.5 分钟白等
2. **半死连接等 300s 太久**: Mac 休眠恢复/WiFi 切换后 TCP 连接看起来还在但对端不响应，要等 read=300s 才发现

### 需求

#### 改动 1: Timeout 后诊断-决策二阶段处理

Timeout 发生后，不盲目重试，先 ping API 端点判断网络状态：

**ping 成功（网络正常）→ 内容太多**:
- 不重试（重试也会超时）
- 返回 `finish_reason="timeout"` 的 LLMResponse
- Agent loop 注入 hint 让模型缩短输出/拆分步骤
- 类似 §60 的 `finish_reason="length"` 截断处理

**ping 失败（网络问题）→ 等恢复**:
- Ping 轮询等待恢复（间隔 10s，最多 20s）
- 恢复后重试正式请求
- 仍不可达则抛出错误

#### 改动 2: 轻量 ping 实现

- 对 `api_base` URL 发 HTTP GET（10s 超时）
- 任何 HTTP 响应（200/401/404/503）= 网络可达
- 只有连接超时/无响应 = 网络不可达
- 不依赖 API key 或模型名

#### 改动 3: 每次 timeout 都诊断

- 不是只对第一次 timeout 做诊断，每次 timeout 都 ping（网络状态可能变化）
- 非 timeout 错误（rate limit、502 等）仍走原有重试逻辑不变

### 涉及文件

| 文件 | 改动 |
|------|------|
| `nanobot/agent/retry.py` | 新增 `is_timeout_error()`, `ping_api()`, `wait_for_recovery()` |
| `nanobot/agent/loop.py` | `_chat_with_retry` timeout 诊断 + `_run_agent_loop` timeout hint |
| `nanobot/agent/subagent.py` | 同上两处修改 |

## §62 系统 Hint 消息不落盘

**状态**: ✅ 已完成 (Phase 58)

### 背景

§61 的 timeout hint 和 §60 的 truncation hint 以 `role: "user"` 通过 `append_message` 落盘到 JSONL。前端重新加载 session 时，这些消息被当作普通用户消息气泡显示，造成困惑。

### 分析

| 消息 | 场景 | 是否落盘 | 是否需要落盘 |
|------|------|---------|-------------|
| `[System] Your previous output was truncated...` | finish_reason=length 截断 | ✅ append_message | ❌ 即时效果，仅当前 turn |
| `[System] ⚠️ Your previous LLM call timed out...` | §61 timeout hint | ✅ append_message | ❌ 计数器是内存状态，落盘后语义过期 |
| `⚠️ [Context Approaching Limit]` | 截断预警 | ❌ 仅内存 | — |
| `⚠️ [Budget Alert]` | 迭代预算告警 | ❌ 仅内存 | — |
| `⚠️ [Context Truncation Notice]` | 截断通知 | ❌ 仅内存 | — |
| `[Preserved user messages...]` | 保留消息 | ❌ 仅内存 | — |

### 方案

删除两处 `append_message` 调用，保留 `messages.append`（内存，LLM 上下文可见）和 `callbacks.on_message`（SSE 实时推送）。

### 改动文件

| 文件 | 改动 |
|------|------|
| `nanobot/agent/loop.py` | 删除截断 hint (L692) 和 timeout hint (L748) 的 `self.sessions.append_message()` |

## §63 Consolidation 孤儿 tool_result 修复 + 400 不重试

**状态**: ✅ 已完成 (Phase 59)
**Commit**: dc7c3987

### 背景

`memory.py` 的 `consolidate()` 按索引切片 `old_messages` 时，切出去作为 consolidation 输入（喂给 LLM 生成 history 摘要）的那部分 messages 没有考虑 tool_use/tool_result 配对，可能包含孤儿 tool_result，导致 Anthropic 返回 400 BadRequestError。同时 400 被当作 retryable error 导致死循环。

### 需求

#### 修复点 ①: Consolidation 输入 messages 清理孤儿

- 文件: `nanobot/agent/memory.py`
- 在 `consolidate()` 方法中，切出去喂给 LLM 做摘要的 messages 部分，确保 tool_use/tool_result 配对完整
- 如果切片边界切断了配对，清理掉孤儿 tool_result（开头的无对应 assistant tool_use 的 tool role 消息）

#### 修复点 ②: 400 BadRequestError 不应被 retry

- 文件: `nanobot/agent/retry.py`
- 在 retry 逻辑中排除 400 状态码（400 是客户端错误，重试没意义）
- 检查位置在 non-retryable message patterns 之后、retryable class names 之前

### 改动文件

| 文件 | 改动 |
|------|------|
| `nanobot/agent/memory.py` | `consolidate()` 中切片后 strip 开头的 orphan tool_result messages |
| `nanobot/agent/retry.py` | `is_retryable()` 中 400 status code 提前返回 False |
| `tests/test_consolidation_orphan.py` | 新增 12 个测试用例 |

## §64 截断预警 Prompt 改进 + 静默清理

**状态**: ✅ 已完成 (Phase 59)
**Commit**: 4fad1354

### 背景

§59 引入的截断预警 prompt 过于冗长，且模型写完 session summary 后 warning/write/result 三条消息留在内存中浪费上下文空间。

### 需求

#### 改动 ①: `_TRUNCATION_WARNING_TEMPLATE` 改为系统提示风格

更简洁的模板，强调"立即写 summary 然后继续任务"。

#### 改动 ②: 新增静默清理机制（Silent Cleanup）

在 tool execution 完成后检测：
- `_warned_this_turn == True`
- response.tool_calls 只有 1 个
- tool_call.name == "write_file"
- path 参数包含 `session_summary/` 且以 `.md` 结尾
- tool result 不是错误

命中后从内存 messages 删除 3 条消息（warning + assistant + tool result），不动 session.messages 和 JSONL。

降级场景均安全：多 tool_calls 不清理、未写 summary 不清理、write_file 失败不清理。

### 改动文件

| 文件 | 改动 |
|------|------|
| `nanobot/agent/loop.py` | 更新 `_TRUNCATION_WARNING_TEMPLATE`；新增 silent cleanup 逻辑 |
| `tests/test_consolidation_orphan.py` | 新增 template 格式验证测试 |

### Hotfix: Silent cleanup 无限循环

**问题**: Silent cleanup 在删除 3 条消息后将 `_warned_this_turn` 重置为 `False`，导致同一 turn 内 warning 被重复注入，LLM 重复写 summary，形成无限循环。

**根因**: `_warned_this_turn = False` 这行代码使得 cleanup 后 Step 3 的 warning 注入条件 `not _warned_this_turn` 重新满足。

**修复**: 移除 `_warned_this_turn = False`，cleanup 后保持 `_warned_this_turn = True`，阻止同 turn 再次注入。`_warned_this_turn` 在下一 turn 开始时自然重置（变量作用域为 while 循环外层）。

**新增测试**: `test_silent_cleanup_does_not_reset_warned_this_turn` — 源码级检查防止回归。
