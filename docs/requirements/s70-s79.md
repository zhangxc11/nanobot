## §70 Consolidation 统一重设计

**状态**: ✅ 已完成 (Phase 62)
**分支**: `feat/consolidation-redesign`
**Commits**: `e444402` ~ `3ba0648` + merge `aee13b1`

### 背景

§66 重写后 consolidation LLM 调用成功率提升至 100%，但 dev 环境长跑测试（session `s69_cons_review_1774181000`）暴露了 **trim 操作**的结构性问题。综合分析发现 7 个 Bug（含 2 个隐藏 Bug），根本原因不是任何单个 Bug 的修复不对，而是：

1. **异步状态散布在 4 个不同位置**：模块级变量（loop.py）、Session 对象（manager.py）、JSONL 文件（磁盘）、pending info（内存 dict），4 处状态、3 种生命周期、2 种写入时机
2. **trim 操作缺少事务性保证**：`_find_tool_aligned_cut` 只检查 cut-1 是否是 assistant(tool_calls)，不处理 multi-tool_call 场景
3. **consolidate() step 8 不做 tool-aligned 对齐**：34.4% 的 session 在 last_consolidated 边界有孤儿 tool_result

#### 7 个已知 Bug

| Bug | 描述 | 不一致的两处状态 |
|-----|------|-----------------|
| §67 | last_consolidated 未持久化到 JSONL | Session 对象 ↔ JSONL 文件 |
| §68 | 跨 AgentLoop 实例状态丢失 | 模块级变量 ↔ Session 对象 |
| Bug1 | `_find_tool_aligned_cut` 不处理 multi-tool_call | trim cut 位置 ↔ 消息结构完整性 |
| Bug2 | `update_metadata(save)` 用旧 lc 覆写 JSONL | JSONL 文件 ↔ Session 对象 |
| Bug3 | pending info 的 archive_cut 基于旧 messages | pending info ↔ 当前 messages 列表 |
| BugA | 失败路径 archive_cut 与 lc 不一致 | pending info ↔ last_consolidated |
| Bug4 | consolidate() step 8 不 tool-aligned | last_consolidated ↔ 消息结构完整性 |

### 需求

用 **3 个核心改动** 替代 7 个独立补丁：

#### R1: ConsolidationState 单例 — 解决 §67, §68, Bug2, Bug3, BugA

**新建 `agent/consolidation_state.py`**（~80 行），用一个类统一管理所有 consolidation 状态：

```python
class ConsolidationState:
    """Singleton managing all consolidation state across AgentLoop instances.
    Replaces: _consolidating, _consolidation_tasks, _consolidation_locks,
              _pending_consolidation_done (4 module-level variables).
    """
    def is_consolidating(key) -> bool
    def pop_pending(key) -> PendingResult | None
    def begin(key) -> asyncio.Lock
    def complete(key, last_consolidated, success)
    def track_task(task)
    def cleanup(key)
```

**关键设计决策**：
- **pending 不再携带 archive_cut**。trim 时从当前 messages 实时计算 cut，不依赖触发时的快照
- **pending 只携带 last_consolidated 和 success**。这是 trim 唯一需要从异步 task 获取的信息
- **lock 是 _SessionState 的一部分**，不再用 WeakValueDictionary，不会被 GC 回收
- `_do_mid_turn_consolidation` 成功/失败后立即 `persist_metadata`，防止 `save()` 覆写

**loop.py 改动**：删除 4 个模块级变量，主循环 Step 1/2/3 改用 `consolidation_state` API。

#### R2: Safe trim with sanitize — 解决 Bug1, BugB

**`_trim_consolidated_messages` 重写**：
- archive_cut 从当前 messages 实时计算（`target_keep = memory_window // 2`），不从 pending info 获取
- trim 后增加 **sanitize 兜底**：删除开头的孤儿 tool_results，不依赖 cut 计算的完美性
- persist 在 trim 内部完成

**`_find_tool_aligned_cut` 增强**：
- Pass 1（§65 原有）：从 assistant(tool_calls) 后退
- Pass 2（§70 新增）：**向前扩展**——收集 `[start:cut]` 范围内所有 assistant 的 tool_call_ids，将 cut 后面属于这些 assistant 的 tool_results 也纳入删除范围

#### R3: last_consolidated tool-aligned — 解决 Bug4

**`consolidate()` step 8 改动**（~5 行）：
- 计算 `raw_lc = len(session.messages) - keep_count` 后，如果 `messages[raw_lc]` 是 tool_result，向前推进跳过所有连续的 tool_results
- 确保 last_consolidated 不会落在 tool_call/tool_result 对之间

### 设计原则

| 原则 | 说明 |
|------|------|
| Single Source of Truth | consolidation 状态只在 ConsolidationState 一处维护 |
| Defensive trim | trim 后做 sanitize 兜底，不依赖完美的 cut 计算 |
| Idempotent persist | 持久化操作幂等，多次调用不会产生不一致 |
| Minimal interface | 对外暴露的 API 不变，改动对 loop.py 主循环透明 |

### 决策记录

| 决策 | 理由 |
|------|------|
| 一步到位（R1+R2+R3 同时实施）而非分步 | Bug2 和 BugA 在长 session 中有实际触发风险，不应延迟修复；总工作量只多 2h |
| pending 不携带 archive_cut | trim 从当前 messages 实时计算，消除了 Bug3（messages 已变但 archive_cut 过时） |
| `_find_tool_aligned_cut` 向前扩展而非向后收缩 | 向后收缩可能退到 start 导致 trim 无效；向前扩展确保 assistant 和所有 tool_results 一起被删除 |
| sanitize 兜底 | 即使 `_find_tool_aligned_cut` 有遗漏，sanitize 也能保证消息列表的完整性 |
